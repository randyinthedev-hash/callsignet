# Callsignet 설계 초안

설계는 아직 진행 중이다. 이 문서는 지금 정해져 있는 것만 적는다.

기업 안에서 도는 머신과 서비스가 서로를 알아보고 인증하는 일을 네트워크 계층이 맡는다. 앱은 상대를 이름으로 부르고, 연결이 맺어지는 순간에 상대가 누구인지 확정된다.

## 이름

Callsignet은 callsign과 signet을 겹쳐 만든 이름이다. callsign은 이름으로 부르는 것이고 signet은 진위를 증명하는 인장이다. 이 설계의 두 축이 그것이다. 한국어로는 콜사이넷이라고 읽는다.

| 약칭 | 무엇인가 |
|---|---|
| csn | Callsignet. 이 리포다. csa끼리 도는 부분을 담는다 |
| wg | WireGuard. 이 설계가 쓰는 터널 프로토콜이다 |
| csa | Callsignet agent. 머신마다 하나 도는 프로그램이다. 터널을 운영하고, 이름을 해석하고, 정책을 집행한다 |

이 리포는 csa끼리 도는 부분을 담는다. csa가 판단에 쓰는 값은 운영자가 적은 로컬 설정 파일에서 온다.

## 전제

앱은 이 체계를 모른다. 앱이 아는 것은 상대의 도메인 이름과 포트뿐이다. 부를 때도 그렇고, 자기에게 붙은 상대를 알아볼 때도 그렇다. 앱 코드를 고치거나 앱 설정을 바꾸는 것을 전제로 하는 기능은 기본이 아니다.

1차 대상은 오래 켜 두고 운영하는 고정형 관리 머신이다. 짧게 떴다 사라지는 워크로드는 범위 밖이다.

## 원칙

정책 판단에 쓰는 신원과 위치는 상대가 주장한 값이 아니라, 패킷을 받은 쪽이 인증하고 관측해서 확정한 값이다. 정책과 감사에 쓰는 IP와 시각도 받은 쪽이 만들어 낸 값이다.

이 설계는 「상대가 누구인가」와 「어디로 연결할 것인가」를 나누어 다룬다.

## 식별

| 개념 | 정의 | 수명 |
|---|---|---|
| peer-id | 조직이 관리하는 자산 이름. 하드웨어를 바꿔도 유지된다 | 첫 등록 때 정해지고 바뀌지 않는다. 폐기해도 다시 쓰지 않는다 |
| 정적 공개키 | wg가 인증에 쓰는 키. 인증의 근거이지 이름이 아니다 | 바꿀 수 있다. peer-id 하나에 여럿 둘 수 있다 |
| 터널 IP | 그 peer에게 배정된 오버레이 주소 | peer-id처럼 드물게 바뀐다. 회수해도 다시 쓰지 않는다 |
| instance-id | 지금 그 peer-id를 맡고 있는 실행 실체. 머신 지문에서 계산한다 | 다시 설치하거나 장비를 교체하면 새로 계산된다 |
| 서비스 이름 | `peer-id/app`. 인스턴스 하나를 가리킨다. 포트는 이름에 넣지 않는다 | 앱 수명 |

이 설계는 이름과 인증 키를 나눈다. 키를 바꿔도 peer-id는 그대로이므로 정책과 로그, 저장해 둔 참조가 깨지지 않는다.

instance-id는 머신이 스스로 대는 값이므로 csa는 정책 판단에 쓰지 않는다. 운영자가 인벤토리를 맞추고 이상을 알아채는 데 쓴다. VM을 복제하면 한 peer-id를 맡은 실체가 둘이 되는데, 이것은 막을 수 없다. 같은 peer-id가 서로 다른 출발지에서 동시에 통신하면 csa 로그에 드러난다.

키를 바꿀 때 조직은 옛 키와 새 키가 함께 유효한 기간을 둔다. 수명이 다해 물러나는 것과 침해되어 거두는 것은 다른 사건이므로 운영자가 사유를 나누어 기록한다. 하나의 공개키가 두 peer-id에 나타나지 않는지는 csa가 기동할 때 검사한다.

## 위치

| 개념 | 정의 |
|---|---|
| 등록된 접속 주소 | 연결을 시도해 볼 후보 주소들. 사내망, NAT 바깥, IPv6처럼 여럿일 수 있다 |
| 관측한 출발지 | 패킷을 받은 쪽 csa가 실제로 본 출발지 |

지금 범위에서 두 csa는 직접 연결만 쓴다. 중계 서버를 두지 않는다. 대상이 사내의 고정형 관리 머신이라 서로 사이에 NAT가 없고 접속 주소가 잘 바뀌지 않기 때문이다. 직접 연결이 되지 않는 구간은 조직이 방화벽 정책으로 푼다.

그래서 받는 쪽 csa는 언제나 출발지를 안다. 다만 그 값은 상대의 고정된 속성이 아니라 그 연결이 맺어지던 때의 망 상황이다. 같은 상대라도 어느 인터페이스로 왔느냐에 따라 달라진다. IP를 조건으로 삼는 정책은 그 사실 위에 선다.

중계는 지사 사이나 이동하는 머신을 지원할 때 다시 본다. 그때는 받는 쪽 csa가 출발지를 알 수 없는 경우가 생기므로 그 경우를 다루는 규칙이 따로 필요해진다.

## 설정

csa가 판단에 쓰는 값은 운영자가 적은 파일에서 온다. 운영자가 적은 파일이 곧 신뢰의 근거다.

형식은 TOML이다. 운영자가 손으로 적고 읽는 파일이므로 주석을 달 수 있어야 하고, 목록이 많아 배열 테이블이 잘 맞는다.

파일은 `/etc/callsignet/` 아래에 셋으로 나눈다. 담는 것이 다르고 바뀌는 주기도 다르기 때문이다. 나누어 두면 설정을 자동으로 만들어 주는 도구가 파일 하나를 통째로 바꿀 수 있다.

| 파일 | 담는 것 |
|---|---|
| `csa.toml` | 이 머신 자신에 대한 값 |
| `peers.toml` | 모든 peer의 이름과 키와 주소와 서비스 |
| `policy.toml` | 이 머신의 정책 |

### csa.toml

```toml
peer-id     = "srv-billing-01"
private-key = "/etc/callsignet/private.key"
domain      = "cs.example.internal"

tunnel-cidr = "10.91.0.0/24"
listen-port = 51820

[tun]
name = "cs0"
mtu  = 1420

[dns]
listen = "127.0.0.54:53"
ttl    = 300
```

`peer-id`는 이 머신이 `peers.toml`에서 자기 항목을 찾는 열쇠다. 자기 항목도 `peers.toml`에 있으므로 터널 IP와 서비스 목록을 그쪽에서 읽는다. 여기에는 개인키 경로만 둔다.

`tunnel-cidr`는 조직이 정한 터널 대역이다. csa는 이 대역으로 가는 경로를 라우팅 테이블에 넣는다.

### peers.toml

```toml
[[peer]]
peer-id    = "srv-billing-01"
public-key = "SG9sZCB0aGlzIGtleSBoZXJlLCBwbGVhc2Uu"
tunnel-ip  = "10.91.0.7"
endpoints  = ["10.0.5.7:51820"]
services   = [{ app = "billing", port = 8080 }]

[[peer]]
peer-id    = "srv-report-02"
public-key = "QW5vdGhlciBrZXkgZ29lcyByaWdodCBoZXJlLg"
tunnel-ip  = "10.91.0.9"
endpoints  = ["10.0.5.9:51820", "10.0.9.9:51820"]
services   = [{ app = "report", port = 8080 }]
```

자기 항목도 여기 있다. 그래야 이름 해석이 자기 서비스와 남의 서비스를 같은 방식으로 다룬다.

`services`가 필요한 까닭은 이름을 풀려면 상대 머신에 어떤 앱이 있는지 알아야 하기 때문이다. csa는 이 목록으로 `report.srv-report-02.cs.example.internal`을 `10.91.0.9`로 답하고, 역방향으로는 `10.91.0.9`를 `srv-report-02.cs.example.internal`로 답한다.

`endpoints`가 여럿이면 csa가 차례로 시도한다.

### policy.toml

```toml
# 이 머신이 붙어도 되는 상대. 나가는 것을 미리 거르는 방어 한 겹이다.
# TOML은 최상위 키를 표보다 먼저 읽으므로 이 줄이 위에 온다.
outbound = ["srv-report-02/report"]

# 이 머신에 붙어도 되는 상대. 집행의 근거다.
[[inbound]]
app   = "billing"
allow = ["srv-report-02", "srv-batch-03"]

# IP 대역만 보는 규칙. 기본은 금지이므로 적을 때 만료 기한을 함께 적는다.
[[inbound]]
app        = "legacy"
allow-cidr = ["10.0.5.0/24"]
expires    = "2026-12-31"
```

### csa가 기동할 때 검사하는 것

csa는 설정을 읽고 다음을 확인한다. 하나라도 어긋나면 기동하지 않고 무엇이 어긋났는지 적는다.

`csa.toml`의 `peer-id`가 `peers.toml`에 있는가. 터널 IP가 peer 사이에 겹치지 않는가. 모든 터널 IP가 `tunnel-cidr` 안에 있는가. `tunnel-cidr`가 이 머신이 이미 쓰는 대역과 겹치지 않는가. 공개키가 두 peer에 겹쳐 나타나지 않는가. `policy.toml`이 가리키는 peer-id와 app이 `peers.toml`에 있는가.

## csa

운영자는 머신마다 csa를 하나 둔다. csa는 TUN 인터페이스를 하나 만들고 그 위에서 wg를 직접 돌린다. TUN 인터페이스는 커널이 보낸 패킷이 밖으로 나가지 않고 그 인터페이스를 열어 둔 사용자 공간 프로그램에게 전달되는 가상 인터페이스다. 커널 wg 장치가 아니므로 `wg` 명령으로는 보이지 않는다. csa는 정적 키를 보관하고, 설정을 읽고, 이름을 해석하고, 정책을 집행한다.

```
머신
├─ 앱
├─ 커널
│   ├─ TCP · UDP · IP · 라우팅
│   ├─ TUN 인터페이스      csa가 만들고 csa가 읽고 쓴다
│   └─ NIC
└─ csa
    ├─ 이름 해석
    ├─ 정책 집행
    ├─ 설정
    └─ wg (사용자 공간)
        ├─ 정적 키
        ├─ 세션 키
        ├─ 암호화와 복호화
        └─ 허용 IP 검사
```

wg는 csa 안에 있다. csa는 커널과 두 자리에서 만난다. TUN 인터페이스에서 안쪽 IP 패킷을 주고받고, UDP 소켓에서 암호화한 패킷을 주고받는다. 두 방향 모두 이 두 자리를 다 쓰며 순서만 반대다.

```
나갈 때    앱 → 커널 → TUN 읽기 → csa 암호화 → UDP 소켓 쓰기 → 커널 → NIC
들어올 때  NIC → 커널 → UDP 소켓 읽기 → csa 복호화·검사·정책 → TUN 쓰기 → 커널 → 앱
```

csa의 UDP 소켓은 평범한 소켓이다. csa가 기동할 때 포트 하나에 바인딩한다. 상대 csa가 보낸 암호화 패킷은 이 머신의 NIC 주소와 그 포트를 목적지로 가지므로, 커널이 목적지 포트로 소켓을 찾아 csa에게 넘긴다. 그 포트는 `peers.toml`의 접속 주소에 들어 있는 포트다.

### wg가 하는 일

앱이 TCP를 쓰든 UDP를 쓰든 커널이 만드는 것은 IP 패킷이다. csa는 그 IP 패킷을 헤더까지 통째로 암호화해 UDP 데이터그램 하나에 담는다.

```
NIC로 나가는 패킷

  바깥 IP 헤더        src = 이 머신의 NIC 주소
                     dst = 상대의 접속 주소
  바깥 UDP 헤더       dst 포트 = 상대 csa가 리슨하는 포트
  wg 헤더      어느 세션인지 가리키는 번호와 카운터
  ─────────── 여기부터 암호화 ───────────
  안쪽 IP 헤더        src = 이 머신의 터널 IP
                     dst = 상대의 터널 IP
  TCP 또는 UDP 헤더   앱이 쓰는 포트
  앱 데이터
```

여기서 따라오는 성질이 넷이다.

망에서 보이는 것은 바깥 IP 헤더와 UDP 헤더와 wg 헤더뿐이다. 안쪽 터널 IP도 앱이 쓰는 포트도 보이지 않는다.

쓰는 것은 UDP 포트 하나뿐이다. 그래서 NAT와 방화벽을 지나기 쉽다.

상대는 정적 공개키로 정해진다. handshake가 끝나면 그 세션이 어느 상대의 것인지 확정된다. 그 뒤 데이터 패킷은 wg 헤더의 세션 번호로 세션을 찾는다.

세션 키는 주기적으로 새로 만든다. 그것은 새로운 접근 승인이 아니다.

상대의 접속 주소가 바뀌면 csa는 받은 패킷의 출발지를 보고 갱신한다. 검증에 통과한 패킷일 때만 갱신한다.

csa는 주기적으로 keepalive를 보낸다. 상태를 기억하는 방화벽이 UDP 흐름을 짧게 만료시키기 때문이다.

csa가 기동할 때 운영체제에 거는 설정은 넷이다.

1. TUN 인터페이스를 만든다.
2. 그 인터페이스에 자기 터널 IP를 붙인다.
3. 터널 대역으로 가는 경로를 라우팅 테이블에 넣는다.
4. 내부 도메인 질의가 자기에게 오도록 이름 해석 설정을 건다.

2번과 3번은 승인 뒤에 한다. 승인 전에는 터널 IP가 없다.

포트 단위로 가르는 일은 라우팅에서 하지 않는다. 라우팅 테이블은 목적지 주소만 보므로 포트로 가르려면 방화벽 표시와 정책 라우팅이 필요하고, 정책이 바뀔 때마다 그 규칙을 다시 써야 한다. 그 판단은 csa가 한다. 라우팅에는 터널 대역 전체를 TUN 인터페이스로 보내는 경로 하나만 둔다.

조건이 둘 있다. csa에게 네트워크 관리 권한이 있어야 TUN 인터페이스를 만들고 경로를 넣을 수 있다. 그리고 조직은 터널 대역으로 사내에서 쓰지 않는 대역을 골라야 한다. 겹치면 원래 가던 트래픽이 터널로 들어간다.

## 이름 해석

csa가 내부 도메인 하나의 이름 해석기가 된다. 앱에게 답을 전달하는 특별한 통로는 없다. 앱은 평소처럼 이름을 해석하고, 그 질의가 csa에 닿아 csa가 표준 DNS 응답을 돌려준다.

csa는 루프백의 전용 주소에서 53번 포트로 리슨한다. 리눅스는 `127.0.0.0/8` 전체가 루프백이므로, csa는 다른 리졸버가 쓰는 주소와 겹치지 않는 주소를 하나 잡는다. 포트를 53으로 두는 이유는 `/etc/resolv.conf`에 포트를 적을 수 없기 때문이다.

csa는 자기 터널 IP의 53번 포트에서도 함께 리슨한다. systemd-resolved가 루프백 주소를 DNS 서버로 받지 않기 때문이다. 아래에서 다시 적는다.

### 리졸버 자리 차지하기

csa는 기동할 때 그 머신의 리졸버 관리 방식을 판별하고 거기에 맞춰 설정을 건다. 관리 방식이 셋이다.

csa는 `/etc/resolv.conf`의 내용을 먼저 보고 판별한다. 적힌 리졸버 가운데 systemd-resolved의 주소인 `127.0.0.53`이 있으면 systemd-resolved가 관리하는 것이다. 다른 주소가 적혀 있으면 그 파일을 csa가 직접 고친다. 아무 주소도 적혀 있지 않을 때만 링크가 어디를 가리키는지 본다. 내용을 먼저 보는 까닭은 링크는 그대로인 채 내용만 다른 경우가 있기 때문이다. 컨테이너와 네트워크 네임스페이스가 그렇다.

systemd-resolved가 관리하면 csa는 TUN 인터페이스에 내부 도메인을 자기에게 보내는 라우팅을 건다. 그 도메인의 질의만 csa에게 오고 나머지 이름은 원래 경로로 간다. TUN 인터페이스가 사라지면 이 설정도 함께 사라진다.

이때 csa가 그 인터페이스의 DNS 서버로 적는 주소는 루프백 주소가 아니라 자기 터널 IP다. systemd-resolved는 링크의 DNS 서버로 루프백 주소를 받지 않고 거절한다. 자기 터널 IP는 그 인터페이스에 붙어 있는 주소이므로 거절당하지 않는다. csa가 두 주소에서 함께 리슨하는 까닭이 이것이다.

이때 터널 대역의 역방향 구역도 함께 등록해야 한다. 역방향 질의는 내부 도메인이 아니라 `in-addr.arpa` 구역으로 가기 때문이다. 터널 대역이 `10.91.0.0/24`이면 `0.91.10.in-addr.arpa`다. 이것을 빠뜨리면 역방향 질의가 회사 DNS로 가서 답을 받지 못한다.

NetworkManager가 관리하면 csa는 NetworkManager 설정에 내부 도메인과 자기 주소를 넣는다. RHEL 계열이 여기 해당한다.

아무도 관리하지 않으면 csa는 `/etc/resolv.conf`를 직접 고친다. 첫 줄에 자기 주소를 넣고 원래 리졸버를 둘째 줄에 남긴다. 이 경우에는 모든 질의가 csa에게 오므로 역방향 구역을 따로 등록할 필요가 없다. 그러면 csa가 멈춰도 내부 도메인 밖의 이름 해석은 둘째 줄로 넘어간다.

`/etc/resolv.conf`가 심볼릭 링크이면 csa는 링크를 따라가 그것이 가리키는 파일을 제자리에서 고친다. 링크 자체는 건드리지 않는다. 파일을 새로 만들어 이름을 바꿔치는 방식을 쓰지 않는 까닭이 이것이다. 이름 바꾸기는 대상이 링크여도 따라가지 않고 링크를 지우므로, 그렇게 하면 그 머신의 이름 해석 설정을 망가뜨린다.

csa가 멈출 때는 같은 파일에 원래 내용을 되돌려 쓴다.

systemd-resolved는 배포판마다 기본 여부가 다르다. Ubuntu는 켜져 있고, Debian과 RHEL 계열과 SUSE는 기본이 아니다. 그래서 한 가지 방법으로 덮이지 않는다.

csa는 설정을 건 뒤 스스로 확인한다. 자기 도메인의 이름 하나를 질의해 응답이 자기에게서 온 것인지 본다. 아니면 설정이 먹지 않은 것이므로 csa는 운영자에게 알린다. 조용히 실패하면 앱이 이름을 찾지 못하는 것으로만 드러나 원인을 찾기 어렵다.

컨테이너 안에서 도는 앱은 그 컨테이너의 리졸버 설정을 따른다. 운영자가 그 설정을 csa의 주소로 잡아 준다. 지금 범위는 머신에서 직접 도는 앱이다.

### 이름과 답

정식 이름은 `peer-id/app`이다. 앱이 DNS로 부를 때 쓰는 이름은 csa가 `app.peer-id.내부도메인` 형태로 기계적으로 바꾼 것이다.

csa는 정방향과 역방향을 모두 답한다. 다만 두 방향이 답하는 이름의 층이 다르다.

정방향은 서비스 이름과 머신 이름을 모두 답한다. `app.peer-id.내부도메인`과 `peer-id.내부도메인`이 둘 다 그 머신의 터널 IP를 가리킨다. 한 머신에 앱이 여럿이면 서비스 이름도 여럿이고 모두 같은 터널 IP를 가리킨다.

머신 이름도 답하는 까닭은 역방향이 답한 이름을 정방향으로 다시 풀 수 있어야 하기 때문이다.

역방향은 터널 IP를 받아 머신 이름인 `peer-id.내부도메인`을 답한다. IP 하나에 이름 하나만 답할 수 있으므로 서비스 이름 가운데 하나를 고를 수 없기 때문이다.

받는 쪽 앱이 알아야 하는 것은 어느 머신에서 왔는가이므로 이것으로 충분하다. 부른 쪽은 클라이언트이고 클라이언트에게는 서비스 이름이 없다. 정책도 `src peer-id` 기준이라 머신 단위다.

csa는 자기가 가진 것 안에서 답한다. `peers.toml`에 적힌 peer의 이름만 답하고 그 밖의 이름에는 답하지 않는다. 다만 이름이 풀리지 않는 것은 정책 집행이 아니다. 최종 판단은 받는 쪽 csa가 한다.

조직은 이름 캐시 수명을 터널 IP가 바뀌는 주기에 맞춰 정한다. 정책이 철회되어도 받는 쪽 csa가 연결을 막으므로 앱의 캐시는 상관이 없다.

## 연결

```
        머신 A                                    머신 B

     ┌──────────┐                              ┌──────────┐
     │    앱    │                              │    앱    │
     └──────────┘                              └──────────┘
       ①│   ▲          앱과 csa 사이는 운영체제가     ▲⑥
        ▼   │②         거친다. 앱은 csa를 모른다.     │
     ┌──────────┐                              ┌──────────┐
     │   csa    │                              │   csa    │
     │ 이름 해석 │                              │ 출발지 검사│
     │ 암호화    │                              │ 정책 판단 │
     └──────────┘                              └──────────┘
          │③                                       ▲
          └────────────  wg  ────────────────┘④⑤
                        직접 연결
```

① 앱이 상대를 도메인 이름과 포트로 부른다. 운영체제가 그 이름을 해석하려고 질의를 보내고, 그 질의가 csa에 닿는다. csa가 터널 IP를 답한다. 앱은 csa가 있다는 것을 모른다.

② 앱이 운영체제에게서 받은 주소와 포트로 연결한다. 앱은 그 주소를 알아보지 않는다. 커널이 그 패킷을 csa의 TUN 인터페이스로 넘긴다.

③ 보내는 쪽 csa가 패킷을 암호화한다. 암호화한 패킷의 바깥 헤더에 적는 목적지 주소는 `peers.toml`에 적힌 상대의 접속 주소다.

④ 받는 쪽 csa가 복호화한다. 복호화가 성공하면 어느 정적 공개키의 세션인지 확정되고, 안쪽 패킷의 출발지가 그 상대에게 배정된 터널 IP인지 검사한다. 여기까지 통과하면 보낸 쪽의 peer-id가 확정된다.

⑤ 받는 쪽 csa가 정책을 보고, 통과한 패킷만 TUN 인터페이스에 쓴다.

⑥ 커널이 평소처럼 앱의 소켓에 배달한다. 앱은 포트를 바인딩하고 상대 주소를 묻는 평소 방식을 그대로 쓴다. 그때 앱에게 보이는 주소는 보내는 쪽의 터널 IP인데, 앱은 그 값을 해석하지 못한다. 앱이 그 주소의 이름을 알아보려고 역방향 질의를 하면 운영체제가 그 질의를 csa에 보내고 csa가 답한다.

### 커널과 csa 사이

터널 대역으로 가는 트래픽만 이 길을 지난다. 그 밖의 트래픽은 라우팅에서 갈려 csa를 거치지 않고 NIC로 나간다.

앱의 TCP는 그대로 살아 있다. 커널이 만든 IP 패킷 하나를 csa가 통째로 암호화해 UDP 데이터그램 하나에 담고, 받는 쪽 csa가 복호화하면 원래 패킷이 그대로 나온다. TCP의 양 끝은 앱과 상대 앱이며, 재전송과 순서 맞추기는 양쪽 커널의 TCP가 한다. wg는 손실을 복구하지 않는다.

TUN 인터페이스는 실제 하드웨어가 아니다. 커널이 그 인터페이스로 보낸 패킷은 밖으로 나가지 않고 csa가 읽어 간다. 그래서 패킷 하나가 커널의 IP 계층을 두 번 지난다.

나갈 때 커널은 라우팅을 두 번 조회한다. 처음에는 앱이 보낸 패킷의 목적지인 터널 IP를 찾아 TUN 인터페이스를 고른다. csa가 그 패킷을 읽어 암호화하고 UDP로 내보내면, 커널이 그 UDP 패킷의 목적지인 상대의 접속 주소를 찾아 NIC를 고른다.

들어올 때 csa는 UDP 소켓에서 패킷을 받으면서 출발지 주소를 함께 얻는다. **관측한 출발지를 얻을 수 있는 자리는 여기뿐이다.** csa가 복호화하고 출발지를 검사하고 정책을 본 뒤 TUN 인터페이스에 쓰면, 커널은 그 패킷을 그 인터페이스로 들어온 것처럼 다루어 앱의 소켓에 배달한다.

csa는 TUN 인터페이스의 MTU를 NIC보다 작게 잡고, 그 크기에 맞춰 TCP 연결의 MSS를 깎는다. 안쪽 패킷에 바깥 헤더가 붙기 때문이다.

앱이 UDP를 쓰는 경우도 같은 길이다. 커널 TCP 계층 자리에 UDP 계층이 올 뿐이다.

### 경로

두 csa 사이에는 wg 세션 하나뿐이다. 보내는 쪽 csa는 `peers.toml`에 적힌 접속 주소로 바로 붙는다. 주소가 여럿이면 차례로 시도한다. 어느 주소로도 붙지 못하면 연결되지 않는다.

앱이 `0.0.0.0`이 아니라 특정 주소 하나에만 바인딩해 두면 터널 IP로 배달된 패킷을 받지 못한다.

## 집행

### 받는 쪽

csa는 연결을 종단하지 않는다. 복호화한 패킷을 TUN 인터페이스에 넣을지 버릴지만 정한다. 복호화를 csa가 하므로 그 패킷이 어느 상대에게서 어느 주소로 왔는지 패킷마다 안다.

flow는 csa가 받아들인 연결 하나다. 승인 수명과 집행의 단위가 이것이다.

### 보내는 쪽

csa는 TUN 인터페이스에서 읽은 패킷의 목적지 터널 IP와 포트를 `policy.toml`의 `outbound` 목록과 맞춰 본다. 목록에 없으면 csa는 암호화하지 않고 버리며 그 시도를 기록한다. 앱이 허가되지 않은 곳에 붙으려 했다는 사실이 여기서 드러난다.

csa는 버릴 때 TUN 인터페이스에 거절 응답을 써서 앱에게 알린다. 조용히 버리면 앱이 연결 시간이 다 갈 때까지 기다린다.

이 걸러내기는 여러 겹 방어 가운데 한 겹이며 최종 판단이 아니다. 최종 판단은 받는 쪽 csa가 한다.

## 정책

정책은 `src peer-id → dst peer-id/app` 형태다.

받는 쪽 csa는 이렇게 판단한다.

- 보낸 쪽의 peer-id를 확정하지 못하면 버린다.
- peer-id만 적혀 있으면 그 peer에서 온 연결은 어디서 왔든 허용한다.
- IP 대역만 적혀 있으면 그 대역에서 왔으면서 등록된 peer인 경우에 허용한다. 기본은 금지이고, 조직이 켤 때 만료 기한을 함께 정한다.
- 둘 다 적혀 있으면 두 조건을 모두 만족해야 한다.
- NAT 뒤의 사설 IP까지 잘게 나누어 지정하지 않는다.

`policy.toml`의 `[[inbound]]` 하나가 규칙 하나다. 한 앱에 규칙을 여럿 적을 수 있고, 받는 쪽 csa는 그 가운데 하나만 만족해도 들인다. 규칙 하나 안에서는 적힌 조건을 모두 만족해야 한다. 조건을 하나도 적지 않은 규칙은 아무도 들이지 않는다. 앱 이름만 적어 둔 것을 열어 두려는 뜻으로 읽지 않는다.

IP 대역이 재는 값은 상대의 터널 IP가 아니라 받는 쪽 csa가 관측한 바깥 출발지다. wg가 복호화하면서 그 상대의 접속 주소로 맞춰 둔 값이며, 인증을 통과한 패킷일 때만 갱신되므로 아무나 이 값을 바꿀 수 없다.

받는 쪽 csa는 wg에게 접속 주소를 물어 1초 동안 들고 쓴다. 묻는 일이 값싸지 않기 때문이다. 그래서 상대가 다른 자리로 옮겨 가면 IP 대역 규칙이 그것을 1초 늦게 안다. 대역은 상대를 확정하는 근거가 아니라 그 위에 더한 조건이므로 이만큼의 늦음을 받아들인다. 대역을 보는 규칙이 걸린 포트일 때만 묻는다.

만료 기한은 받는 쪽 csa가 판단할 때마다 본다. 설정을 읽을 때만 보면 csa가 오래 도는 동안 기한이 지나가도 규칙이 살아 있게 된다. 기한은 적은 날짜의 0시에 지난다. 마지막으로 규칙이 도는 날은 그 앞날이다. 날짜는 그 머신의 시간대로 읽는다.

기한이 지나면 그 규칙 전체가 죽는다. 같은 규칙에 적은 peer-id도 함께 죽는다. 기한은 규칙의 성질이지 대역만의 성질이 아니기 때문이다. 기한 없이 늘 들일 상대가 있으면 규칙을 따로 적는다.

같은 승인이 양쪽에 다른 모습으로 놓인다. 보내는 쪽 설정에는 그 머신이 붙어도 되는 목록이 있고, 받는 쪽 설정에는 그 머신에 붙어도 되는 목록이 있다. 집행의 근거는 받는 쪽 목록이다. 보내는 쪽 목록은 이름을 풀고 나가는 것을 미리 거르는 방어 한 겹이며 최종 권한이 아니다.

허락하고 철회하는 일은 운영자가 `policy.toml`을 고쳐서 한다.

## 상태와 로그

csn 단독으로 돌 때 csa가 보관하는 상태는 정적 개인키 하나뿐이다. `csa genkey`가 만들고 소유자만 읽을 수 있게 권한을 건다. 그 밖의 값은 모두 설정 파일에서 읽으므로 csa를 다시 띄워도 잃을 것이 없다.

csa는 다음을 로그에 적는다.

연결을 받아들이거나 버린 일이다. 시각, 보낸 쪽 peer-id, 관측한 출발지, 목적지 app과 포트, 판단 결과를 적는다.

나가는 연결을 미리 거른 일이다. 앱이 허가되지 않은 곳에 붙으려 했다는 사실이 여기 남는다.

이름 질의에 답한 일이다. 어떤 이름을 무엇으로 답했는지 적는다.

설정을 다시 읽은 일과 검사에 실패한 일이다.

| `csa check` | 설정만 검사하고 끝낸다. 기동하기 전에 쓴다 |
| `csa status` | 지금 붙어 있는 상대와 마지막 handshake 시각을 보여 준다 |
| `csa reload` | 도는 중에 설정을 다시 읽는다 |
| `csa genkey` | 정적 키쌍을 만든다 |

`csa status`와 `csa reload`는 도는 csa에게 물어야 하므로 통로가 하나 필요하다. csa run은 유닉스 소켓을 하나 열고 거기서 물음을 받는다. 소켓 경로는 `/run/callsignet/<peer-id>.sock`이고 소유자만 붙을 수 있다.

소켓 이름에 peer-id를 넣는 까닭은 한 머신에서 csa를 여럿 띄우는 경우가 있기 때문이다. 통합 하네스가 그렇게 한다. `csa status`는 설정 디렉터리에서 peer-id를 읽어 어느 소켓에 붙을지 정한다.

`csa reload`는 도는 csa에게 설정을 다시 읽으라고 이른다. 다시 읽는 것은 도는 csa가 자기가 기동할 때 받은 디렉터리에서 한다. `csa reload`에 주는 설정 디렉터리는 어느 소켓에 붙을지 알아내는 데만 쓴다.

csa는 다시 읽은 설정 가운데 걸 수 있는 것만 건다. `peers.toml`과 `policy.toml`은 도는 중에 갈아 끼울 수 있다. `csa.toml`은 그럴 수 없다. 거기 적힌 값은 TUN 인터페이스와 개인키와 리슨 주소를 정하므로 바꾸려면 csa를 다시 띄워야 한다. `peers.toml`에서 이 머신 자신의 공개키와 터널 IP도 마찬가지다.

그런 것이 바뀌었으면 csa는 아무것도 걸지 않고 운영자에게 다시 띄우라고 알린다. 일부만 걸면 운영자가 무엇이 도는지 알 수 없기 때문이다. 검사에 걸린 설정도 걸지 않는다. csa는 앞서 읽은 설정 그대로 계속 돈다.

csa는 wg에 바뀐 상대만 건다. 바뀌지 않은 상대를 다시 걸면 wg가 들고 있던 관측한 접속 주소를 `peers.toml`에 적힌 값으로 되돌린다. 그러면 그 상대가 옮겨 간 자리를 잃는다. 공개키가 바뀐 상대는 wg에게 다른 상대이므로 csa가 옛 키를 먼저 지운다.

`csa status`는 이 머신에 대해 인터페이스와 터널 IP와 도메인, 이름 해석 관리 주체, MTU와 TCP MSS 한도와 지금까지 깎은 횟수를 보여 준다.

`csa status`는 상대마다 다섯 가지를 보여 준다. peer-id, 터널 IP, 관측한 출발지, 마지막 handshake 시각, 주고받은 바이트다. 이 가운데 뒤의 셋은 도는 csa가 wg에게 물어 얻는다.

관측한 출발지는 세션을 맺은 상대에게만 적는다. 아직 맺지 않은 상대에 대해 wg가 내놓는 주소는 `peers.toml`에 적힌 값이고, 그것은 csa가 관측한 것이 아니기 때문이다.

한 번도 세션을 맺지 못한 상대인데도 보낸 바이트가 0이 아닐 수 있다. csa가 그 상대에게 보내려 한 패킷이 있으면 wg가 handshake를 걸어 보고, 그때 나간 바이트가 여기 잡히기 때문이다. 받은 바이트가 0인 채 보낸 바이트만 늘어나면 그 상대가 답하지 않는다는 뜻이다.

## wg 특성에서 오는 문제

Callsignet은 wg 위에 선다. 아래는 그 특성에서 나오는 것이므로 도입할 때 미리 확인한다.

### MTU와 패킷 조각화

**증상** — 작은 요청은 오가는데 큰 응답에서 멈춘다. 데이터베이스 대량 조회나 파일 전송에서 나타난다.

**원인** — wg가 원래 IP 패킷에 바깥 헤더를 덧붙인다. IPv4로 나가면 최소 60바이트, IPv6면 80바이트가 더 붙는다. 그래서 기존 MTU인 1500을 넘겨 조각이 나거나 버려진다. 중간 방화벽이 ICMP를 버리면 경로 MTU 발견도 되지 않아 조용히 사라진다.

**확인** — 조각화 금지 비트를 세운 ping을 크기를 키워 가며 보내 어느 크기부터 가지 않는지 본다. 그 크기가 TUN 인터페이스의 MTU보다 작으면 이 문제다.

**조치** — TUN 인터페이스의 MTU를 1420 이하로 잡는다. 그래도 증상이 남으면 1360까지 낮춘다.

csa가 두 가지를 스스로 한다. 첫째, 기동할 때 터널 MTU가 바깥 인터페이스의 MTU 안에 들어가는지 견주어 적는다. 상대의 접속 주소로 가는 경로를 물어 그 인터페이스의 MTU를 읽고, `tun.mtu`에 wg가 덧붙이는 60바이트를 더한 값과 견준다. 들어가지 않으면 얼마로 낮추라고 알린다. 막지는 않는다. 조직이 알고 그렇게 두는 경우가 있다.

둘째, csa가 나르는 TCP SYN에 실린 최대 세그먼트 크기를 터널이 나를 수 있는 크기로 깎는다. 나가는 쪽과 받는 쪽 양쪽에서 한다. 상대가 깎지 않고 보내는 경우가 있기 때문이다. 라우터나 방화벽에서 따로 깎지 않아도 된다.

앱이 그 머신에서 직접 돌면 커널이 터널 경로의 MTU를 보고 알아서 정하므로 csa가 깎을 일이 드물다. 경로에 `advmss`가 걸려 있거나 앱이 스스로 크기를 정한 경우에 깎는다. 그래서 csa는 몇 번 깎았는지를 세어 `csa status`에 보여 준다. 운영자가 이 값을 보고 깎기가 실제로 도는지 안다.

### 방화벽이 UDP를 막는다

**증상** — 어떤 두 머신 사이에서만 연결이 되지 않는다.

**원인** — 그 구간의 방화벽이 UDP를 막는다. 기업 방화벽이 UDP를 엄격히 막는 경우가 있다.

**확인** — 그 구간에서 csa가 쓰는 UDP 포트로 패킷이 나가고 되돌아오는지 본다.

**조치** — csa가 쓰는 UDP 포트를 연다. 기본값은 51820이다. 이 설계에는 중계 서버가 없으므로 그 포트를 열지 못하면 그 구간은 연결되지 않는다.

### 방화벽이 UDP 세션을 일찍 지운다

**증상** — 한동안 쓰지 않던 연결이 다음에 쓸 때 멈춘다.

**원인** — 상태를 기억하는 방화벽이 UDP 흐름의 유지 시간을 TCP보다 훨씬 짧게 잡는다. 30초인 경우가 흔하다.

**확인** — 멈춘 연결에 패킷을 한 번 보내 보고 그 뒤에 살아나는지 본다. 살아나면 중간 장비가 흐름을 지운 것이다.

**조치** — csa가 keepalive를 25초마다 보낸다. 흔한 만료 시간인 30초보다 짧아야 한다.

### L2에 기대는 시스템이 동작하지 않는다

**증상** — 멀티캐스트나 브로드캐스트로 서로를 찾는 클러스터가 구성원을 찾지 못한다. IP를 쓰지 않는 오래된 프로토콜이 동작하지 않는다.

**원인** — wg는 L3 터널이다. IP 패킷만 나르며 MAC 주소 기반의 L2 통신과 브로드캐스트를 나르지 않는다. NetBEUI나 IPX처럼 IP가 아닌 프로토콜은 아예 지나가지 못한다.

**확인** — 그 소프트웨어가 구성원을 어떻게 찾는지 설정을 본다. IP가 아닌 프로토콜을 쓰는지도 함께 본다.

**조치** — 일반적인 TCP와 UDP 애플리케이션은 문제가 없다. 구성원을 찾는 방식이 문제라면 목록을 직접 적는 방식으로 바꾼다. L2 통신 자체가 꼭 필요하면 Callsignet 위에 VXLAN 같은 L2 터널을 한 겹 더 얹거나, 그 구간을 Callsignet 밖에 둔다.

### QoS와 DPI 장비가 트래픽을 구분하지 못한다

**증상** — QoS 장비가 Callsignet 트래픽의 우선순위를 낮춘다. 침입 탐지 장비와 방화벽 로그가 안쪽을 보지 못한다.

**원인** — 그 장비들에게는 전부 암호화된 UDP 한 종류로 보인다. 안쪽 IP 헤더와 앱이 쓰는 포트까지 암호화되기 때문이다.

**확인** — 도입 전에 어떤 장비가 무엇을 보고 있었는지 목록을 만든다.

**조치** — QoS는 바깥에서 보이는 값으로 걸 수 있다. 네트워크 장비 정책에 csa가 쓰는 UDP 포트와 머신의 NIC 주소로 우대 정책을 반영한다. 안쪽을 보던 항목은 대신할 수 없으므로, 그 일을 csa 로그가 맡을 수 있는지 도입 전에 확인하고 합의한다. 나중에 발견하면 되돌리기 어렵다.

### 대용량 전송이 느리다

**증상** — 백업이나 복제처럼 큰 트래픽에서 속도가 나지 않는다.

**원인** — 이것은 wg가 아니라 우리 선택에서 온다. csa가 사용자 공간에서 암호화와 복호화를 하므로 패킷마다 커널과 사용자 공간 사이를 오간다.

**확인** — 같은 구간에서 Callsignet을 거치지 않을 때와 견준다. csa의 CPU 사용도 함께 본다. csa가 한 코어를 다 쓰고 있으면 이 문제다.

**조치** — 근본 대응은 없다. 연결마다 출발지를 알기 위해 치른 값이다. 그 머신에 코어를 더 주거나, 그 트래픽을 Callsignet 밖에 두고 기존 경로로 보낸다.

## 나중에 볼 것

### 중계

지금은 직접 연결만 쓴다. 지사 사이나 클라우드와 사내 사이처럼 직접 연결이 되지 않는 구간을 덮으려면 암호화된 패킷을 그대로 전달하는 중계 서버가 필요하다.

중계를 넣으면 받는 쪽 csa가 상대의 출발지를 알 수 없는 경우가 생긴다. 그때를 어떻게 다룰지가 함께 정해져야 한다. IP를 조건으로 삼는 정책과 감사 기록이 그 값에 기대고 있다.

### eBPF와 mTLS로 도는 구조

wg와 TUN 인터페이스를 쓰지 않는 변형이다. eBPF의 `cgroup/connect4` 훅으로 앱의 연결을 csa의 로컬 소켓으로 돌리고, csa가 상대 csa와 mTLS 연결을 맺어 나른다. 받는 쪽 csa는 상대 인증서로 peer-id를 확정하고 정책을 본 뒤 앱에게 넘긴다.

wg 특성에서 오는 문제를 피하려고 둔다. UDP를 막는 구간에서도 돌고, TCP가 로컬에서 끝나므로 MTU 문제가 없으며, 기존 장비가 TCP 연결로 보므로 QoS 정책을 걸기 쉽다.

CA를 두지 않고 자체 서명 인증서를 쓰되 그 안에 그 peer의 정적 공개키를 담는다. 받는 쪽 csa는 그 공개키가 설정에 있는 값과 같은지 본다. wg가 하던 확정을 TLS가 대신할 뿐 근거는 그대로다.

이름 체계와 정책 집행 위치와 관측한 출발지는 그대로다. 앱도 고치지 않는다.

잃는 것은 IP 계층을 통째로 나르는 성질이다. 소켓 계층에서 가로채므로 TCP 위주가 되고, UDP는 `cgroup/sendmsg4`로 따로 다뤄야 하며, 그 밖의 프로토콜은 나르지 못한다. cgroup v2와 일정 버전 이상의 커널이 필요하다.

### 보내는 쪽을 서비스 단위로 거르기

지금 csa는 TUN 인터페이스에서 IP 패킷만 읽으므로 어느 프로세스가 만들었는지 모른다. eBPF의 `cgroup/connect4` 훅을 붙이면 연결을 만든 cgroup을 알 수 있고, systemd가 서비스마다 cgroup을 만드니 그것이 곧 서비스다. 보내는 쪽 걸러내기가 머신 단위에서 서비스 단위로 내려간다.

보내는 쪽은 최종 판단 주체가 아니므로 방어가 한 겹 두꺼워지는 것이다.

### 여러 인스턴스를 하나로 묶는 이름

지금은 앱이 인스턴스를 직접 부른다. 그래서 서비스가 다른 머신으로 옮겨 가면 앱 설정을 고쳐야 한다. 이 이름이 생기면 정책 표현과 승인 단위도 그 이름을 쓴다. 받는 쪽 집행은 그대로 보낸 쪽의 peer-id를 기준으로 한다.
