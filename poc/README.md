# 실험

설계가 주장하는 것을 관측으로 만든다. 리눅스에서 root로 돌린다. 네임스페이스와 wg 인터페이스를 만들기 때문이다.

## cryptokey routing 확인

설계는 받는 쪽 csa가 상대를 확정한다고 말한다. 그 근거는 wg의 동작이다. wg는 복호화한 패킷의 출발지 IP가 그 상대에 허용된 목록 안에 없으면 버린다. 그래서 상대의 정적 공개키로 인증된 세션이라도 배정된 터널 IP만 출발지로 쓸 수 있다.

이 실험은 그것을 잰다. 네임스페이스 둘을 만들어 wg로 잇고, 허용된 출발지와 허용 목록 밖 출발지로 각각 패킷을 보낸 뒤 받는 쪽 `wg0`의 통계가 어떻게 갈리는지 본다. 허용 목록 밖에서 온 패킷은 `rx_packets`를 올리지 않고 `rx_errors`만 올린다.

```bash
sudo apt update && sudo apt install -y wireguard-tools iproute2 iputils-ping
make preflight
sudo make setup
sudo make check
sudo make teardown
```

기록은 `results/cryptokey-<시각>.md`로 저절로 만들어진다. 키는 `poc/cryptokey/_work/`에 남으며 커밋하지 않는다.

## 실제 IP로 부른 연결을 터널로 돌리기

설계는 앱이 상대를 지금 쓰는 실제 IP와 포트로 불러도 csa 둘이 터널로 나른다고 주장한다. 그 근거는 커널의 nftables NAT과 연결 추적이다. 보내는 쪽 머신의 NAT 표가 상대의 실제 IP와 서비스 포트로 가는 패킷의 목적지를 상대의 터널 IP로 바꾸고 출발지를 자기 터널 IP로 바꾼다. 그러면 그 패킷은 TUN 인터페이스로 들어가 지금과 같은 안쪽 패킷이 된다. 받는 쪽 머신의 NAT 표가 터널로 온 패킷의 목적지를 자기 실제 IP로 바꾸고 출발지를 상대의 실제 IP로 바꾼다. 그러면 앱은 상대를 실제 IP로 본다. 커널의 연결 추적이 되돌아가는 패킷과 거절 응답의 주소를 되돌린다.

csa는 아직 이 규칙을 만들지 않는다. 이 실험은 네임스페이스 둘에 지금의 csa를 띄운다. 스크립트가 NAT 표를 손으로 건다. 그 뒤 다음을 잰다. 앱이 상대의 실제 IP로 TCP와 UDP를 맺고 자료가 오간다. 출발지를 바꾸지 않으면 받는 쪽 wg가 허용 IP 검사에서 버린다. 실제 IP 하나에만 바인딩한 서버가 받고 상대를 보낸 쪽의 실제 IP로 본다. 정책에 없는 상대의 실제 IP로 붙으면 앱이 곧바로 `EHOSTUNREACH`를 받는다. 듣는 앱이 없는 포트로 붙으면 앱이 `ECONNREFUSED`를 받는다. 상대 csa가 죽어 있으면 실제 IP로 불러도 서지 않는다. 그때 보내는 쪽 표를 지우면 같은 연결이 직통으로 인증 없이 통한다. 스크립트는 역경로 검사(`rp_filter`)를 엄격으로 두고 잰다.

```bash
sudo make steer
```

기록은 `results/steer-<시각>.md`로 저절로 만들어진다. 작업 파일은 `/var/tmp/csn-steer-work/`에 남는다. csa는 개인키 위의 모든 디렉터리를 다른 사용자가 고칠 수 없어야 받아들인다. 리포 체크아웃이 0775인 머신이 있으므로 작업 파일을 리포 밖에 둔다.
