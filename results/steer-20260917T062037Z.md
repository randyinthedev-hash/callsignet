## 틀림 셋의 까닭

틀림 셋은 모두 시험 스크립트의 잘못이다. 스크립트가 `kill`로 상대 csa를 멈추려 했는데 그 신호가 csa에 닿지 않았다. 스크립트는 csa를 셸 함수(`nsb`)를 거쳐 배경에 띄웠고, 함수를 배경에 띄우면 `$!`가 서브셸의 PID가 된다. `kill`은 그 서브셸만 죽였고 csa는 고아로 남아 계속 돌았다. 상대 csa의 로그에 그 뒤 시각(15:20:34, 15:20:36)의 기록이 남아 있다.

그래서 셋째 묶음의 검사는 살아 있는 상대 csa를 잰 것이다. 직통 경로 표가 남아 있던 것은 csa가 살아 있었기 때문이다. 「인증 없이 통했다」고 적힌 연결은 실제로는 터널로 간 연결이다. 상대 csa의 로그에 그 연결이 「들어온 연결을 받았습니다. 상대 srv-a」로 남아 있다. 보내는 쪽 표를 지운 뒤 직통으로 붙지 못한 것은 상대 csa의 직통 경로 표가 그 연결을 버렸기 때문이다. 설계의 주장과 어긋난 관측은 없다.

다음 커밋에서 스크립트가 csa를 함수를 거치지 않고 띄우게 고쳤고, 시험을 다시 돌린 기록을 따로 둔다. 이 실행이 남긴 csa 둘과 UDP 서버는 다음 실행이 시작하면서 거둔다.

보내는 쪽(srv-a)의 표와 계수기:

```
table ip callsignet-nat {
	chain output {
		type nat hook output priority dstnat; policy accept;
		ip daddr 10.90.1.30 tcp dport 8080 counter packets 4 bytes 240 dnat to 10.91.1.2
		ip daddr 10.90.1.30 udp dport 8080 counter packets 0 bytes 0 dnat to 10.91.1.2
		ip daddr 10.90.1.30 tcp dport 9090 counter packets 0 bytes 0 dnat to 10.91.1.2
		ip daddr 10.90.1.30 udp dport 9090 counter packets 1 bytes 32 dnat to 10.91.1.2
		ip daddr 10.90.1.50 tcp dport 8080 counter packets 1 bytes 60 dnat to 10.91.1.3
		ip daddr 10.90.1.50 udp dport 8080 counter packets 0 bytes 0 dnat to 10.91.1.3
	}

	chain postrouting {
		type nat hook postrouting priority srcnat; policy accept;
		oifname "cs0" ip saddr != 10.91.1.0/24 counter packets 6 bytes 332 snat to 10.91.1.1
	}

	chain prerouting {
		type nat hook prerouting priority dstnat; policy accept;
		iifname "cs0" ip daddr 10.91.1.1 counter packets 0 bytes 0 dnat to 10.90.1.10
	}

	chain input {
		type nat hook input priority srcnat; policy accept;
		iifname "cs0" ip saddr 10.91.1.2 counter packets 0 bytes 0 snat to 10.90.1.30
		iifname "cs0" ip saddr 10.91.1.3 counter packets 0 bytes 0 snat to 10.90.1.50
	}
}
```
